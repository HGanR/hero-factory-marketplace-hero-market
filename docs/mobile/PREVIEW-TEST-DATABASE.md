# Preview test database — schema, seed, privileges, and target checks (DRAFT)

Prepared 2026-10-29 by Aura. **NOT RUN.** Nothing here has been executed
against any database, and nothing has been provisioned. Review the scripts
before first use. No secret values appear here. Passwords generated by the
seed script must never be committed to Git or pasted into chat.

## What this is

The minimal implementation for the isolated test database behind the
protected mobile Preview (see `PREVIEW-DEPLOYMENT-CHECKLIST.md`):
one table, five synthetic accounts, and the checks that prove the login
path behaves. It is based on the committed code at
`e26b3dd932fec6b627a5a675725047e381343957` (branch
`feat/smart-trust-mobile-preview-20261026`).

## Files

- `../../apps/mobile-preview/scripts/test-schema.sql` — `marketplace_users`
  transcribed from `src/lib/db/schema.ts` (`marketplaceUsers`). The login
  route selects the entire row, so the complete 15-column definition is
  preserved. The definition carries no foreign keys, and both inspected
  routes (marketplace login, mobile session) touch only this table, so
  no other table is required for the preview login path.
- `../../apps/mobile-preview/scripts/seed-test-database.mjs` — seeds five
  synthetic accounts. Dry run by default (prints the plan, connects to
  nothing). Passwords are generated locally with `crypto.randomBytes`
  and hashed with `bcrypt.hashSync(password, 10)` — the same function and
  cost factor as `hashPassword` in `src/lib/auth.ts`. Two active/approved
  users exist for account-switch testing; unapproved, inactive, and
  no-password accounts are covered. The script reads only
  `TEST_DATABASE_URL` (never `DATABASE_URL`), requires `--apply` plus
  `--database <name>` matching the URL, refuses database names containing
  "prod", pre-flights the table's columns against the expected set, and
  touches only rows with the five synthetic emails. TLS follows the
  website's own rule (`src/lib/db/mysql2-connection-options.ts`):
  TiDB Cloud hosts and `TEST_DATABASE_SSL=1/true/required` force TLS
  with certificate verification.
- `../../apps/mobile-preview/scripts/check-preview-accounts.mjs` — target
  checks against a deployed Preview URL. Account cases read a local
  credentials file (written by the seed script with mode 0600, kept
  outside the repository). Unknown-user, missing-user-session, and
  expired-token cases are separate tests in this script, not seed rows.

## How to run (after review, on first use)

From `apps/mobile-preview`, after `npm ci` (the scripts use only the
target's pinned dependencies — `bcryptjs`, `mysql2`, `jsonwebtoken` —
plus Node built-ins):

```sh
# 1. Dry run — plan only, no connection:
node scripts/seed-test-database.mjs

# 2. Apply schema + seed (isolated test database only):
TEST_DATABASE_URL='<test-database URL>' \
  node scripts/seed-test-database.mjs --apply-schema --apply --database <test-database-name> \
  --write-credentials-file <path-outside-the-repo>/preview-credentials.json

# 3. Run target checks against the Preview URL:
PREVIEW_JWT_SECRET='<preview-only secret>' \
  node scripts/check-preview-accounts.mjs \
  --base-url <preview-url> --credentials-file <path-outside-the-repo>/preview-credentials.json
```

The credentials file holds test passwords. Keep it outside the
repository, mode 0600, and delete it when the test database is retired.
Without `PREVIEW_JWT_SECRET`, the two token cases report SKIP, not
failure. `PREVIEW_JWT_SECRET` must be the same preview-only secret as
the deployment's `JWT_SECRET`; it is used only to mint test tokens in
memory and is never printed.

## Required database privileges

Two separate credentials. Never reuse the production credential, and
never give the preview credential seed privileges.

**Preview runtime credential** (used by the Vercel Preview deployment
as `DATABASE_URL`; database-scoped, least privilege):

- `SELECT`, `UPDATE` on `<test-database>`.`marketplace_users` only.
  The login path reads the row and updates `lastLogin`; nothing else
  in the preview login path writes.
- TLS required in transit (enforced by the connection code for TiDB
  Cloud hosts; set `DATABASE_SSL=required` if the host rule ever fails
  to engage — `DATABASE_SSL` is optional hardening, not a required
  variable).
- No `CREATE`, `DROP`, `DELETE`, `GRANT`, or access to any other
  database.

**Seed credential** (one-time local use by the person running the seed
script; a different credential from the preview runtime):

- `SELECT` on `INFORMATION_SCHEMA.COLUMNS` (pre-flight column check),
  plus on `<test-database>`.`marketplace_users`: `SELECT`, `INSERT`,
  `DELETE` (scoped by the script to the five synthetic emails), and
  `CREATE TABLE` only if `--apply-schema` is used.
- Retire or rotate it after seeding. Never store it in Git, chat, or
  the Vercel project.

Template (fill in database, user, and host at provisioning time; no
values are recorded here):

```sql
-- Preview runtime (least privilege):
GRANT SELECT, UPDATE ON `<test-database>`.`marketplace_users`
  TO '<preview-user>'@'<allowed-hosts>' REQUIRE SSL;
-- Seed (one-time, local):
GRANT SELECT, INSERT, DELETE ON `<test-database>`.`marketplace_users`
  TO '<seed-user>'@'<allowed-hosts>' REQUIRE SSL;
-- Only if applying the schema with the seed credential:
GRANT CREATE ON `<test-database>`.* TO '<seed-user>'@'<allowed-hosts>' REQUIRE SSL;
```

## Target checks

The checks script asserts, against the Preview URL:

- Both active/approved users sign in; switching between them works;
  the profile check returns the signed-in user.
- Wrong password → 401; unapproved → 403; inactive → 403; no password
  set → 403 — all with the generic sign-in failure message.
- **Separate test — unknown user:** an identifier with no row → 404
  with the generic message.
- **Separate test — missing-user session:** a valid 7-day token for a
  user id with no row → 403 on the profile check. This needs no
  "deleted" flag; the profile route explicitly checks for a missing
  user.
- **Separate test — expired token:** a token past its expiry → 401
  "Your session has expired."
- Logout clears the session; the next profile check returns 401.

Manual checks still required (see the deployment checklist): confirm in
the Vercel dashboard — without sharing values — that the preview
project's `DATABASE_URL` points at the isolated database, not the
production one (different host and/or database name); Deployment
Protection challenge before accounts; `no-store` on private responses.

## Database service — working assumption, confirmation still needed

The website's connection code is written for TiDB Cloud
(`src/lib/db/mysql2-connection-options.ts`: TLS is forced for
`tidbcloud` / `.tidbcloud.com` / `.tidb.io` hosts, with a TiDB-specific
error message). That is strong evidence the website runs on TiDB Cloud,
but the live connection string itself was not read (it is a secret),
so the provider is **not confirmed from code alone**. Working
assumption for the isolated preview database: a separate TiDB Cloud
database (separate cluster or database within the account) with a
database-scoped credential, so the same TLS handling applies
unchanged. Confirm the provider and the cost before provisioning
anything. Nothing has been provisioned by this PR.

## Limits

- Scripts are NOT RUN: no execution against any database, no live
  verification of the DDL transcription, the bcrypt parameters, or the
  check assertions. First run requires a code review and a dry run.
- The DDL index names are local to the test schema; Drizzle-generated
  names may differ. Uniqueness behavior is what matters.
- The seed script's "prod" name refusal is a guardrail, not proof of
  isolation: the operator must still confirm the target database in
  the Vercel dashboard before the first login.
- Test accounts must never be copied into, or used against, the
  production database.
