# Preview test database — schema, seed, privileges, and target checks (DRAFT)

Prepared 2026-10-29 by Aura. Corrected 2026-10-29 per Charles's three
reviews of the scripts (logout/jar semantics, account switching,
credential-file output, checker target validation, database isolation,
missing-user establishment; then USAGE grants, credential-file races
and symlinks, read-only missing-user proof, removal of the
existing-rows escape hatch, and count-only refusals; then seed
failure handling — refusals bypassing cleanup, and committing before
passwords are saved — plus binding the missing-user proof to the same
database and id). **NOT RUN against any real database.** Nothing has
been provisioned or seeded. Review the scripts before first use. No
secret values appear here. Passwords generated by the seed script
must never be committed to Git or pasted into chat.

## What this is

The minimal implementation for the isolated test database behind the
protected mobile Preview (see `PREVIEW-DEPLOYMENT-CHECKLIST.md`):
one table, five synthetic accounts, and the checks that prove the login
path behaves. It is based on the committed code at
`e26b3dd932fec6b627a5a675725047e381343957` (branch
`feat/smart-trust-mobile-preview-20261026`).

## Files

- `../../apps/mobile-preview/scripts/test-schema.sql` — `marketplace_users`
  transcribed from `src/lib/db/schema.ts` (`marketplaceUsers`). The login
  route selects the entire row, so the complete 15-column definition is
  preserved. The definition carries no foreign keys, and both inspected
  routes (marketplace login, mobile session) touch only this table, so
  no other table is required for the preview login path.
- `../../apps/mobile-preview/scripts/preview-test-helpers.mjs` — pure,
  dependency-free decision logic shared by the scripts and the tests:
  cookie jar, checker target validation, seed target parsing and
  confirmation, grant danger check (USAGE distinguished from real
  privileges), column diff, symlink-resolving private-output-file
  destination rules, test-token mint/verify (HS256 via node:crypto),
  missing-user proof validation, and the SeedRefusal error type.
- `../../apps/mobile-preview/scripts/seed-runner.mjs` — the seed
  orchestration, separated from the CLI so its failure handling is
  injectable and testable without a live database. It never exits and
  never prints passwords; it throws SeedRefusal (with an exit code)
  for refusals. Its contract: credentials are generated and SAVED
  (flushed) BEFORE the transaction is attempted; if the commit outcome
  is uncertain (commit throws) or a post-commit step fails, recovery
  credentials are PRESERVED and the caller must warn loudly; if
  failure happens before the commit is attempted, the saved output is
  DISCARDED (nothing was committed); the transaction is rolled back
  whenever it was begun and the commit did not succeed.
- `../../apps/mobile-preview/scripts/seed-test-database.mjs` — thin CLI
  over the runner: guards, credentials-file establishment, connection,
  and a single exit-code mapping after all cleanup has run. It never
  exits mid-flow, so a refusal after the credentials file is opened
  still removes the empty file. Passwords are generated locally and
  hashed with `bcrypt.hashSync(password, 10)` — the same function and
  cost factor as `hashPassword` in `src/lib/auth.ts`. Two
  active/approved users exist for account-switch testing; unapproved,
  inactive, and no-password accounts are covered. The script reads only
  `TEST_DATABASE_URL` (never `DATABASE_URL`). The target host and
  database must be explicitly confirmed (`--confirmed-host`,
  `--confirmed-database`) and must match the URL exactly — substring
  rules are not used. Before deleting or inserting anything, the
  runner refuses when the table holds account rows outside the
  synthetic set; there is no escape hatch, and refusals print a row
  count only, never an existing account's email or row contents.
  Third-party packages load only after every guard passes, so a
  rejected target causes zero database activity. The credentials file
  destination is resolved through symlinks, must lie outside the
  repository, and is created exclusively ('wx', mode 0600) BEFORE any
  database change; a failed run removes the empty file it created.
  TLS follows the website's own rule
  (`src/lib/db/mysql2-connection-options.ts`): TiDB Cloud hosts and
  `TEST_DATABASE_SSL=1/true/required` force TLS with certificate
  verification.
- `../../apps/mobile-preview/scripts/verify-missing-user-id.mjs` —
  read-only proof that a user id is absent from the test database
  (single SELECT, own `TEST_READONLY_DATABASE_URL` variable, same
  confirmed-target guards). With `--proof-file` it writes a
  machine-checkable proof record {userId, host, port, database, rows:
  0, checkedAt}, created exclusively ('wx', mode 0600) outside the
  repository. Run it before the checker; the checker validates the
  proof against the id and database it is about to use, so the absence
  check demonstrably applies to the same database and id. The remaining
  link — that host/database is the preview deployment's actual
  `DATABASE_URL` target — is operator-confirmed in the Vercel
  dashboard; no script here can see the deployment's connection string.
- `../../apps/mobile-preview/scripts/check-preview-accounts.mjs` — target
  checks against a deployed Preview URL, using a shared cookie jar that
  models the browser. Account cases read a local credentials file
  (written by the seed script with mode 0600, kept outside the
  repository). Unknown-user, missing-user-session, and expired-token
  cases are separate tests in this script, not seed rows. The checker
  requires `--base-url` AND `--confirmed-origin` (exact origin match,
  HTTPS only), rejects URLs containing credentials, and never follows
  redirects (`redirect: 'manual'`; a 3xx outcome fails the case).
  Deployment Protection is not disabled: `PREVIEW_PROTECTION_BYPASS`
  (the bypass secret from the Vercel project's Deployment Protection
  settings, for automation) is sent as the `x-vercel-protection-bypass`
  header. Logout is verified by processing the clearing Set-Cookie and
  requesting the profile with the jar empty — the old JWT is never
  re-sent, because the application clears the cookie and does not
  revoke the token. The missing-user case requires `--missing-user-id`,
  `--missing-user-proof`, `--missing-user-db-host`, and
  `--missing-user-db-name`; a proof for a different id or database, or
  no proof at all, reports SKIP instead of risking a false pass,
  because the 403 for a missing user is identical to the 403 for an
  inactive/unapproved account.
- `../../apps/mobile-preview/tests/preview-guards.test.mjs` — executable
  regression tests (see "Test results" below). No build, no database.

## How to run (after review, on first use)

From `apps/mobile-preview`, after `npm ci` (the scripts use only the
target's pinned dependencies — `bcryptjs`, `mysql2` — plus Node
built-ins; the checker itself needs no third-party packages):

```sh
# 1. Dry run — plan only, no connection:
node scripts/seed-test-database.mjs

# 2. Apply schema + seed (isolated test database only):
TEST_DATABASE_URL='<test-database URL>' \
  node scripts/seed-test-database.mjs --apply-schema --apply \
  --confirmed-host <test-host> --confirmed-database <test-database-name> \
  [--write-credentials-file <path-outside-the-repo>/preview-credentials.json]

# 3. Prove the missing-user id is absent (read-only) and write proof:
TEST_READONLY_DATABASE_URL='<read-only test-database URL>' \
  node scripts/verify-missing-user-id.mjs \
  --user-id <id> --confirmed-host <test-host> --confirmed-database <test-database-name> \
  --proof-file <path-outside-the-repo>/missing-user-proof.json

# 4. Run target checks against the Preview URL:
PREVIEW_JWT_SECRET='<preview-only secret>' \
PREVIEW_PROTECTION_BYPASS='<Vercel protection bypass secret>' \
  node scripts/check-preview-accounts.mjs \
  --base-url <preview-url> --confirmed-origin <preview-origin> \
  --credentials-file <path-outside-the-repo>/preview-credentials.json \
  [--missing-user-id <id> --missing-user-proof <path-outside-the-repo>/missing-user-proof.json \
   --missing-user-db-host <test-host> --missing-user-db-name <test-database-name>]
```

In file mode the seed script NEVER prints passwords; they live only in
the credentials file, which is created exclusively, must not already
exist, and must lie outside the repository (symlinks resolved, both
enforced). The credentials file holds test passwords: keep it outside
the repository, mode 0600, and delete it when the test database is
retired. Without `PREVIEW_JWT_SECRET`, the two token cases report SKIP,
not failure. `PREVIEW_JWT_SECRET` must be the same preview-only secret
as the deployment's `JWT_SECRET`; it is used only to mint test tokens
in memory and is never printed.

If the seed fails AFTER the commit was attempted, do not simply
re-run it: the credentials were preserved (file kept, or recovery
output printed) precisely because the database state is uncertain.
Verify the table manually first, then decide whether to re-seed or
use the preserved credentials.

## Required database privileges

Three separate credentials. Never reuse the production credential, and
never give the preview credential seed privileges.

**Preview runtime credential** (used by the Vercel Preview deployment
as `DATABASE_URL`; database-scoped, least privilege):

- `SELECT`, `UPDATE` on `<test-database>`.`marketplace_users` only.
  The login path reads the row and updates `lastLogin`; nothing else
  in the preview login path writes.
- TLS required in transit (enforced by the connection code for TiDB
  Cloud hosts; set `DATABASE_SSL=required` if the host rule ever fails
  to engage — `DATABASE_SSL` is optional hardening, not a required
  variable).
- No `CREATE`, `DROP`, `DELETE`, `GRANT`, or access to any other
  database.

**Seed credential** (one-time local use by the person running the seed
script; a different credential from the preview runtime):

- `SELECT` on `INFORMATION_SCHEMA.COLUMNS` (pre-flight column check),
  plus on `<test-database>`.`marketplace_users`: `SELECT`, `INSERT`,
  `DELETE` (scoped by the script to the five synthetic emails), and
  `CREATE TABLE` only if `--apply-schema` is used. The script also
  reads `SHOW GRANTS` as a best-effort check and refuses plainly
  dangerous grants — `USAGE` alone is not dangerous; any other
  privilege on the global scope, `ALL PRIVILEGES`, `GRANT OPTION`, and
  FILE/SUPER/SHUTDOWN/RELOAD/DROP/CREATE USER are. Provisioning-time
  restriction is the real control.
- Retire or rotate it after seeding. Never store it in Git, chat, or
  the Vercel project.

**Read-only credential** (for `verify-missing-user-id.mjs` only):

- `SELECT` on `<test-database>`.`marketplace_users` only. The script
  issues one SELECT and nothing else.

Template (fill in database, user, and host at provisioning time; no
values are recorded here):

```sql
-- Preview runtime (least privilege):
GRANT SELECT, UPDATE ON `<test-database>`.`marketplace_users`
  TO '<preview-user>'@'<allowed-hosts>' REQUIRE SSL;
-- Seed (one-time, local):
GRANT SELECT, INSERT, DELETE ON `<test-database>`.`marketplace_users`
  TO '<seed-user>'@'<allowed-hosts>' REQUIRE SSL;
-- Only if applying the schema with the seed credential:
GRANT CREATE ON `<test-database>`.* TO '<seed-user>'@'<allowed-hosts>' REQUIRE SSL;
-- Read-only proof (missing-user id):
GRANT SELECT ON `<test-database>`.`marketplace_users`
  TO '<readonly-user>'@'<allowed-hosts>' REQUIRE SSL;
```

## Target checks

The checks script asserts, against the Preview URL, on one shared
cookie jar:

- User 01 signs in, profile is user 01; user 02 signs in, profile
  changes to user 02; user 01 signs in again, profile changes back.
- Wrong password → 401; unapproved → 403; inactive → 403; no password
  set → 403 — all with the generic sign-in failure message — and the
  session is still user 01 afterwards.
- **Separate test — unknown user:** an identifier with no row → 404
  with the generic message.
- **Separate test — missing-user session:** a valid 7-day token for an
  id PROVED absent by the read-only check (proof file validated for
  the same id and database) → 403 on the profile check. This needs no
  "deleted" flag; the profile route explicitly checks for a missing
  user. Without a valid proof the case reports SKIP instead of
  risking a false pass.
- **Separate test — expired token:** a token past its expiry → 401
  "Your session has expired."
- Logout clears the cookie (clearing Set-Cookie processed, jar empty);
  the next profile check with no cookie returns 401.

Manual checks still required (see the deployment checklist): confirm in
the Vercel dashboard — without sharing values — that the preview
project's `DATABASE_URL` points at the isolated database, not the
production one (different host and/or database name); Deployment
Protection challenge before accounts; `no-store` on private responses.

## Test results (executed — separate from syntax checks)

Run 2026-10-29 in Aura's VM, Node v24.22.1, no build, no database,
no external network:

```sh
cd apps/mobile-preview && node --test tests/preview-guards.test.mjs
# tests 36, pass 36, fail 0
```

What the 36 tests execute: everything from the previous 25 (cookie-jar
semantics; checker origin validation; seed target parsing/confirmation;
grant danger detection with the USAGE distinction; column diff;
symlink-resolving destination rules and count-only refusal messages;
token mint/verify; missing-user-id validation; CLI-level proofs that
rejected seed, verifier, and checker targets cause zero network/
database activity; a full checker pass against a local fake preview;
redirect refusal), plus the new failure-handling coverage: the seed
runner against an injected fake connection and fake credentials store
— success saves before commit; dangerous-grant, missing-column, and
unexpected-row refusals before any save or transaction; save failure
discards with no transaction; insert failure rolls back and discards;
commit failure preserves recovery credentials and rolls back;
verification mismatch after commit preserves credentials; USAGE grants
accepted at runner level; missing-user proof validation binding the
same id and database (including wrong-id, wrong-database, wrong-host,
nonzero-rows, and missing-timestamp rejections); the checker skipping
the missing-user case without a valid proof (no proof, and a proof
for a different database); and a static guard that the seed CLI and
runner never call process.exit mid-flow. The 36 passing tests remain
Aura's reported execution; they have not been independently rerun.

What was NOT executed: any path that needs a real MySQL server — the
seed's connect/schema/insert/verify flow, the grant-list read, the
column/existing-row pre-flights against a live table, the read-only
absence proof against a live table, and the proof-file write. Those
remain NOT RUN until a reviewed first run against the isolated test
database. Syntax checks (`node --check` on all files) also pass, and
are reported separately from the executed tests above.

## Database service — working assumption, confirmation still needed

The website's connection code supports TiDB Cloud compatibility
(`src/lib/db/mysql2-connection-options.ts`: TLS is forced for
`tidbcloud` / `.tidbcloud.com` / `.tidb.io` hosts). That supports
compatibility; it does not by itself prove which service the deployed
website uses, and no production connection string needs to be shared
to confirm that. Working assumption for the isolated preview database:
a separate TiDB Cloud database with a database-scoped credential, so
the same TLS handling applies unchanged. Confirm the provider and the
cost before provisioning anything. Nothing has been provisioned by
this PR.

## Limits

- The DDL index names are local to the test schema; Drizzle-generated
  names may differ. Uniqueness behavior is what matters.
- The seed script's exact-match host/database confirmation is a
  guardrail, not proof of isolation: the operator must still confirm
  the target database in the Vercel dashboard before the first login.
- The proof file binds the absence check to the same id and database
  strings the checker is told to use; it cannot prove the preview
  deployment points at that database — that link is the dashboard
  check above.
- Test accounts must never be copied into, or used against, the
  production database.
